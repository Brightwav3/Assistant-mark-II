### Passed

- `memory.explicit.rejected` correctly reported
  `MEMORY_EXPLICIT_TRIGGER_REQUIRED` for:
  `Zapomněl jsem, že mám rád plechovky.`
- `memory_create` did not create a durable memory. The later
  `memory.candidate.stored` event was only an episode candidate, not a confirmed
  explicit memory.

### Failure and root cause

The delegated model returned a completed-looking `memory_create` result after
the Tool System had returned `invalid_arguments`. MARK consequently said that
the fact had been stored even though the runtime had rejected it. The source
guard itself was safe; the delegation boundary lost the failed tool outcome
before validating the model's final JSON.

The repair is recorded in ecosystem ADR 0003:

- `ActionRuntime` now carries the parent request id into Tool System;
- the voice delegation tool refuses an obvious memory-write request without an
  explicit remember trigger before it starts background work;
- Assistant Runtime correlates non-successful tool outcomes to that request;
- the broker publishes `DELEGATION_TOOL_FAILED` instead of
  `delegation.completed` and does not deliver the result to the voice session.

The regression is `a failed memory tool cannot become a completed delegation`.
The fix passes offline; a new hardware run must repeat both the negative phrase
and the positive explicit phrase `Zapamatuj si, že mám rád plechovky.`.

## Failure observed

After `handoff.committed`, the old physical session closed as expected. The
runtime, however, was still waiting on `session.done` from the original
physical session. That promise resolved when the old session closed, and
`AssistantRuntime` interpreted it as the end of the entire logical interaction.

The trace then shows a later `activation.detected`, a new logical session, and a
new `realtime.greeting.sent`. The user heard:

```text
Dobrý den, jsem MARK, jak vám mohu pomoci pane?
```

The replacement itself did not greet. `openReplacement()` does not send the
opening prompt; the greeting came from the later fresh `interaction` session.

The run also ended with two `memory.episode.closed` events. Therefore this was
not a clean one-conversation handoff and must not be labelled `VERIFIED`.

The raw trace also contains `delegation.delivery.dropped` with `NO_SESSION` for
the silent compaction result. That console event is diagnostic noise around the
compaction path; compaction itself completed and prefilling succeeded. The
user-facing delegated lookup was later delivered to the replacement. It is kept
in the record because the trace should not be rewritten after the fact.

## Root cause

The public `RealtimeCoreAdapter.open()` handle had the lifecycle of the first
physical provider session, even though handoff replaces that session while the
logical interaction continues.

The resulting sequence was:

```text
handoff closes old physical session
  -> old physical session.done resolves
  -> AssistantRuntime clears current interaction
  -> later activation is accepted
  -> new physical session and new greeting
  -> second logical episode
```

This was not fixed by suppressing the greeting. The greeting was a symptom of
the runtime accepting a new interaction after it had incorrectly ended the
old one.

## Local correction

`assistant-runtime/src/adapters.ts` now gives `open()` a logical lifecycle:

- `done` resolves only when the active physical session ends, the logical handle
  is explicitly closed, or the adapter shuts down;
- closing a superseded physical session during handoff does not resolve `done`;
- the logical `close()` closes all physical sessions still attached to that
  interaction, including the replacement;
- handoff-specific `openReplacement()` and `closeSession()` remain physical
  operations.

The decision and rationale are recorded in
[ADR 0004](../../../assistant-runtime/docs/decisions/0004-logical-interaction-lifecycle.md).

The regression test is:

```text
assistant-runtime/tests/handoff-wiring.test.ts
closing the superseded physical session does not finish the logical interaction
```
